# Admin Visibility Spike — School-Admin Aggregate View into Tune Your Brain

Scoping pass for D4 (`LEADERSHIP_DECISIONS_REQUIRED.md`) — now answered as **Option 3: both classroom-level and school-wide aggregates, permission-gated** (2026-09-21). This is a design/scoping pass only — no code written. Per `CLAUDE.md`'s own rule ("write the access matrix before building any endpoint that gates access... share it, confirm it, implement once against it"), the matrix below needs confirmation before any code is written.

## Real gap found while researching this, not assumed from docs

**`learning_events.school_id` is never populated on write, despite the schema having a dedicated `idx_school_created (school_id, created_at)` index built for exactly this kind of query.** Confirmed by reading `server/routes/learning-events.js`'s actual `INSERT` — it only ever sets `user_id`/`student_id`, `event_type`, `game_id`, `skill_id`, `content_version`, `metadata_json`. `school_id` was designed into the Phase 1 schema (the column and its index both exist) but never wired up. **This means every `learning_events` row generated by every Tune Your Brain game since Phase 3 (Calm Down Corner through today's 3 new games) has `school_id = NULL`** — no admin-facing query can group by school until this is fixed, and a historical backfill decision has to be made (see below).

## School_id resolution (new, not previously designed)

Two principal types write events (`server/routes/learning-events.js`'s `getPrincipal()`), and school resolution differs for each:

- **Site-user principal** (a teacher/site-user playing a game directly): `license_seats.registered_site_user_id = user_id` → `purchases.school_id`.
- **PIN-student principal** (the common case — students play through a classroom assignment): `classroom_students.classroom_id` → `classrooms.teacher_site_user_id` → `license_seats.registered_site_user_id` → `purchases.school_id`.

Both resolve through the teacher's own registered seat — there's no direct student→school link today, which is correct (students aren't `site_users` and shouldn't be). Proposed: one shared helper, `resolveSchoolIdForPrincipal(principal)` in `server/lib/` (new file or added to an existing one — `school-admin-assignment.js` is the closest existing home), called from `learning-events.js`'s `POST /` before insert. A site_user with no registered seat (e.g. a non-teacher account) or a classroom whose teacher has no seat both resolve to `NULL` — same as today, just now the *intentional* null case instead of every row being null.

**Historical backfill is a real, separate decision, not automatic.** Existing rows can be backfilled with a one-off script (resolve each distinct `user_id`/`student_id` once, `UPDATE ... WHERE school_id IS NULL`) — cheap, no schema change. Whether to bother is a data-value judgment: worth asking whether admin visibility should show data from launch, or only from whenever this ships forward. Recommend backfilling — it's a few hours of games' worth of data at most (Tune Your Brain launched services 2026-09-16), and it costs nothing to do.

## Access matrix (per `CLAUDE.md`'s own required format)

| Role | Own classroom aggregate | School-wide aggregate | Individual student detail |
|---|---|---|---|
| Anonymous | NO | NO | NO |
| Teacher (site_user, no admin role) | YES (their own classrooms only) | NO | NO — matches existing `student_reflections`/free-text exclusion (§5.6, §10.2) |
| School admin, `read_only`/`secondary` permission | YES (via their own classrooms if also a teacher) | YES (their assigned school(s) only) | NO |
| School admin, `primary` permission | YES | YES (their assigned school(s) only) | NO |
| District admin | — (not scoped by this pass; existing `district_license_admins` follows the same shape one level up, deferred) | — | NO |
| FNE admin (`admin_users`) | YES (any) | YES (any school) | NO — same exclusion applies to FNE staff too, per §10.2's blanket policy, not just school admins |

**"Individual student detail" stays NO for every role, including FNE admin, on purpose.** §10.2 explicitly excludes individual student learning detail from admin visibility, and the whole point of this feature is *aggregate* participation/engagement — not a new backdoor into per-student data. "Aggregate" here means counts (sessions started, completed, badges earned, games played) grouped by classroom/school/game/competency/time — never a per-student row. This is the same posture Branching Scenario's `freeReflection` steps already take (never transmitted at all) — this feature doesn't touch that data class either way, since `learning_events` never carries reflection text (`sanitizeMetadata()` already caps it to small structured primitives).

**Permission-level distinction (`primary` vs `secondary`/`read_only`) doesn't actually gate anything extra for this specific feature** — re-reading D4's own Option 3 more carefully, the real distinction the blueprint intends is school-wide-vs-classroom-only, and every existing school-admin permission level already gets school-wide access to *licensing* data (`/reports` has no permission-level branching today). Recommend: **any active school admin assignment (any permission level) sees their school's aggregate** — matches existing precedent exactly, no new permission tier invented. Flagging this correction explicitly since it revises D4's own recommendation slightly once checked against how permission levels are actually used elsewhere in this codebase.

## Proposed API surface

New `type=tune-your-brain` branch on the existing `GET /api/school-admin/reports` endpoint (same `purchaseId`-scoped, `req.schoolAdmin.purchaseIds`-checked pattern every other report type already uses — no new route file, no new auth pattern):

```
GET /api/school-admin/reports?purchaseId=X&type=tune-your-brain
→ {
    totalSessions, totalCompletions,
    byGame: [{ slug, name, sessionsStarted, completions }],
    byDomain: [{ domain, sessionsStarted, completions }],      // literacy/math/executive/sel/wellness
    byBand: [{ band, sessionsStarted, completions }],
    badgesEarned: N,
    activeStudents: N,           // distinct student_id count, no names/rows
    dateRange: { from, to },
  }
```

A second endpoint or `scope=school` query param variant covers the school-wide rollup (same shape, aggregated across every classroom at that school rather than one teacher's). FNE-admin equivalent reuses the identical query shape from `admin-downloads.html`'s existing admin route pattern, scoped by `admin_users` auth instead of `requireSchoolAdmin`.

## Proposed UI

A new tab or card on `admin-licenses.html`'s existing per-school view (reuses the "Find a School" domain-search UI already built) rather than a brand-new page — Tune Your Brain usage is a property of a school's existing license record, same as seat counts already shown there. For the school-admin portal side, a new card on `school-admin-dashboard.html` (which already exists and already shows licensing-adjacent info) rather than a new page.

## Explicitly deferred, flagged not defaulted

- **District-level rollup** — one level up from school, same shape, not scoped by this pass. Revisit once school-level ships and is trusted.
- **Time-range filtering / trends over time** — first version can be all-time totals; a date-range picker is a real feature, not a given.
- **Per-competency (CASEL) breakdown in the aggregate** — technically easy (`casel_competencies` is already on `brain_games`), deferred only because nothing has asked for it yet; flagging since it's cheap to add to `byGame`'s query if wanted.

Recommend building and deploying (1)+(2) first, independently — verifying real `school_id` values start populating correctly before building any UI on top of them, rather than building the whole stack blind.
