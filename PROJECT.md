# Fixer Nation Education — Project Notes

Production site and admin backend for Fixer Nation Education, live at **fixernationeducation.com**, hosted on Hosting.com/cPanel. A real Node/Express + MariaDB application — not a demo. This file describes **current state** (every real page, feature, and business rule as of the date below) — for history of what shipped when, see `CHANGELOG.md`.

**Maintenance rule (standing convention — see `CLAUDE.md`/`AGENTS.md`):** update this file in the same commit as any change that adds/removes a page, changes a gating rule, or changes a known limitation. This file is what a new developer (human or AI) should read first to understand what the app actually does today — keep it honest.

*Last full rewrite: 2026-08-23, via a from-scratch code survey (not just prior notes) covering every HTML page and every `server/routes/*.js` file.*

**Current direction: v1** (teal/coral, serif headings). The `-v2` set (navy/amber, Second Step-inspired mega-nav) was an earlier alternate direction reviewed and decided against — those files are kept for reference but are frozen, not under active development, and are not described further in this doc.

## Architecture

- **Backend:** Node/Express (`server/`), MariaDB. Deployed via cPanel's "Setup Node.js App" at `repositories/fixernation/server`, mounted at `fixernationeducation.com/api` — all Express routes live under `/api/*`.
- **Frontend:** plain HTML/CSS/vanilla JS, no build step, no framework. Shared client-side includes (`nav.js`, `footer.js`, `site-auth.js`, `admin-common.js`/`admin-nav.js`, `school-admin-nav.js`, `district-admin-nav.js`, `logo-crop-widget.js`, `cart.js`, `pdf-modal.js`) are injected via `<script src="...?v=N">` tags — bump the `?v=N` cache-bust on every page that references a shared file whenever that file changes (browsers cache these indefinitely otherwise). `district-admin-nav.js` deliberately reuses `school-admin-common.css`'s `.sa-*` classes rather than a parallel CSS system for a two-page portal. **No third-party fonts or scripts on pages:** every page loads `fonts.css` (Fraunces, Plus Jakarta Sans, Inter in `assets/fonts/`, bump `fonts.css?v=N` if it changes) and `pdf-modal.js` loads PDF.js from `vendor/pdfjs/3.11.174/`, so visitors' IP addresses are not sent to Google or Cloudflare; `server/test/self-hosted-assets.test.js` enforces it. Remaining outside requests happen only on request (Cloudinary how-to videos on play, YouTube/Vimeo embeds, Unsplash on public marketing pages).
- **Three independent JWT-in-cookie auth systems, deliberately never able to satisfy one another's middleware** (`server/lib/session.js`):

  | Cookie | Max age | Covers | Login route |
  |---|---|---|---|
  | `fn_session` | 24h | The single admin account (`admin_users`) | `server/routes/auth.js` |
  | `fn_user_session` | 30 days | `site_users` — teachers, school license admins, district admins, parents, community members, consumers | `server/routes/site-auth.js` |
  | `fn_student_session` | 8h (one school day) | `classroom_students` — PIN-based, no email at all | `server/routes/classroom-auth.js` |

  **Session invalidation** (site-user only): `site_users.session_invalidated_at` + a JWT `iat` check in `requireSiteAuth`. Set on password change/reset and on any admin action that revokes access (seat unregister, license suspend/cancel/delete-by-domain, both expiry crons) — closes the gap where `hasActiveLicense()` re-checks live but a still-valid 30-day cookie would otherwise keep working for non-license-gated pages (roster tools, classroom management, community). Admin (`fn_session`) sessions have **no revocation mechanism at all** — a pure JWT check, by deliberate lower-priority decision.
  **Known bypass, confirmed intentional (do not "fix" without asking):** an admin with an active `fn_session` in their browser sees full unlocked content on every public page in that same browser, independent of whatever the site-user nav shows — this occasionally reads as a contradiction during dogfooding but is by design.

- **File uploads:** `/api/uploads`, real files for book covers (legacy), curriculum videos/documents, blog images, avatars, community post attachments, Morning Boost audio clips.
- **Curriculum file serving:** never linked directly from `/uploads/` — always through `GET /api/curricula/:id/file?resource=<name>` (or `?doc=<index>`), which enforces the access matrix below and logs to `curriculum_downloads`. Rendered client-side via `pdf-modal.js` (PDF.js from cdnjs) — no native browser PDF viewer, no direct URL exposure.
- **Deploy workflow:** commit → push to GitHub (`github.com/ooWOWZERoo/FixerNation`, public repo — never commit real PII or secrets) → `./deploy.sh` in cPanel Terminal (git pull, rsync, npm install + migrations + restart-flag when `server/` changed). See `CLAUDE.md` for the exact command chain; schema changes to *existing* tables always need a manual one-off `server/scripts/alter-*.js` since `migrate.js` only ever runs `CREATE TABLE IF NOT EXISTS`.
- **`server/db/schema.sql` is a stale base snapshot, not the live schema.** Many now-load-bearing columns/tables (`purchases.license_status`/trial fields/`school_domain`/`invoice_id`/`quote_id`, `school_license_admins`, `school_audit_log`, `parent_student_invitations`, `site_user_audiences`, etc.) only exist via `server/scripts/alter-*.js` migrations layered on top. Don't trust `schema.sql` alone for "what tables/columns exist today."

## Licensing, checkout & quotes

**Five distinct ways a license or book gets purchased**, all real and live except where noted:

| # | Entry point | Route | Payment | Live today? |
|---|---|---|---|---|
| 1 | Cart (`cart.html`) — books + fixed-tier license products | `POST /api/checkout/create-cart-session` | Stripe Checkout | Coded, **blocked on real `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`** — every card path throws at call time without them, no graceful fallback |
| 2 | Cart — Purchase Order | `POST /api/checkout/create-po-order` | None (PO) | **Live** |
| 3 | `licenses.html` standalone — flat single/group license | `POST /api/checkout/create-session` | Stripe Checkout | Stripe-blocked, same as #1 |
| 4 | `licenses.html` standalone — variable-seat / trial product | `POST /api/checkout/create-session` | Stripe Checkout | Stripe-blocked, same as #1; confirmed working end-to-end against **Stripe test-mode keys** via the e2e suite |
| 5 | Quote acceptance (`accept-quote.html`) | `POST /api/quote-accept/accept` | Card or PO | PO branch live; card branch Stripe-blocked |

PO is explicitly the designed fallback so "a school isn't blocked waiting on their business office" — it's the only checkout path guaranteed to work with zero external configuration.

**License data model:** `purchases` (one row per order line — `product_type` book/single_license/group_license/membership; `payment_status` paid/pending; `license_status` pending/scheduled/active/expiring_soon/suspended/cancelled/expired/converted; `school_domain` — a real, normalized email domain, distinct from `quote_requests.school`'s free-text display name) → `license_seats` (single_license = 1 seat pre-filled with buyer's email; group_license = N unassigned seats; a signup matching a seat's `invited_email`, and for group licenses matching the school domain too, auto-claims it) → `license_products` (admin-editable catalog; flags for `call_for_quote`, `variable_seats`, `is_trial`/`trial_days`/`trial_lesson_limit`, `auto_assign_group_id`, `duration_days`). Access (`hasActiveLicense()`) requires a `registered` seat AND a license status not in pending/expired/cancelled/suspended AND not past `expiration_date`. The nightly expiry crons switch every seat off and tag it `inactive_reason = 'license_expired'`; renewing through `PUT /api/newsletter/purchases/:id/license-dates` (status active/expiring_soon/scheduled) restores exactly the tagged seats (`lib/seat-renewal.js`), never seats a school admin deactivated by hand. Nothing else (classrooms, rosters, lesson picks) is deleted at expiry. **Student data retention:** nothing deletes student data on a schedule except Brain Games `learning_events` older than 400 days; removing a student only hides them (`is_active = 0`). The agreed rule (delete 60 days after 31 July for a classroom's school year, with a teacher download and reminders) is specified in `docs/reference/student-data-retention-requirements.md` and not yet built; `server/lib/student-retention.js` holds the date rules and `server/scripts/report-student-retention.js` is the read-only report.

**License length and expiration are computed, not just manually typed.** `license_products.duration_days` (admin dropdown: 30/60/90/180 days, 1 year, or no fixed length) is the catalog default. Every purchase snapshots it onto its own `license_duration_days` at creation time — same "never affected by a later catalog change" principle already used for `amount_cents`/trial fields — scaled by `quoted_term_years` for a quote-accepted purchase. `effective_date`/`expiration_date` are then auto-computed from that snapshot: immediately for card/manual purchases, or on PO receipt for PO purchases (below) — an admin can still hand-override either date afterward. `admin-invoice-print.html` shows "Effective Date" (the invoice's own send date) and, when derivable, "Renewal Date". A persistent top-of-portal banner on both `school-admin-nav.js` (that school's own expiration, color-coded, follows the multi-school selector) and `district-admin-nav.js` (a summary alert across all the district's schools, since there's no single "district license") surfaces this to admins without them having to go looking. A new daily cron (`quote-expiring-reminder.js`) reminds a quote recipient 7 days before `quote_valid_until` if unaccepted — soft reminder only, doesn't block late acceptance.

**Bill To and Ship To (Release 97):** an invoice keeps its own Bill To and Ship To (`invoices.bill_to_*`, `bill_to_saved_at`, `ship_to_*`); `bill_to_saved_at` NULL means an older invoice that still reads Bill To from the contact. Editing (`PUT /api/invoices/:id/addresses`, FNE admin, audited as `invoice_addresses_updated`) changes that invoice only. New invoices (cart PO in `checkout.js`, accepted quotes in `quote-accept.js`) save both blocks at creation through `lib/invoice-parties.js` `insertInvoice` (from the quote, else the CRM contact). Quotes carry `bill_to_*` address and `ship_to_*` columns; the contact has optional `ship_to_*`; the email for quotes and invoices shows both blocks. Rules: `docs/reference/invoice-bill-ship-to-requirements.md`.

**Quote seats (Release 95):** on the Annual tab of the quote builder, "Additional Seats" are free (no per-seat charge) and are added to the tier's seats: `quoted_seat_count` is the license's total seats and `quoted_addon_seats` records how many were added. Arithmetic lives in `quote-seats.js` (shared with the tests). The Add-On Seats tab still prices seats at `license_products.addon_rate_cents`. `server/scripts/report-quote-added-seats.js` is a read-only report of older accepted quotes whose license came up short. Rules: `docs/reference/quote-added-seats-requirements.md`.

**Quote lifecycle:** a quote starts one of two ways — inbound request (`POST /api/contact/quote`, from the public site) or **admin-initiated outbound outreach** (`POST /api/contact/quotes`, a "+ New Quote" button on `admin-quotes.html`). Outbound quotes open the **exact same modal** used to view/edit any quote — same pricing tabs, tiers, school domain, status, notes, content profile — just with the contact fields (name/email/school/phone) blank and editable instead of pre-filled from an inbound request; those contact fields are editable on every quote now, not only new ones. A not-yet-created quote is transparently inserted (`origin='admin'`, tagged "Outbound" in the list) the first time it's saved or sent. Either way: admin builds & sends from `admin-quotes.html` (tier/add-on-seats/term/discount, custom price override, sets `quoted_school_domain` separately from the free-text school name, and picks a **Quote Content Profile** — see below) → buyer opens `accept-quote.html?token=` → accepts by card or PO. The **PO branch claims the quote atomically** (`UPDATE ... WHERE accepted_at IS NULL`) before creating anything, closing a double-submit race that used to create duplicate purchases/invoices. A quoted **trial** product is always `group_license` sized to the product's own `seat_count` (not hardcoded to 1 — a multi-seat trial, e.g. a 5-seat pilot, grants all 5), with the buyer auto-claiming one seat immediately (`autoClaimEmail`, same instant-access guarantee a single-seat trial always had) and the rest starting `available` to invite teachers into; deliberately kept off the domain-based self-registration flow (`school_domain` stays NULL for a trial) so a stranger at a matching email domain can't silently consume a spare seat. PO acceptance requires a PO number and creates a real `unpaid` invoice, forcing `license_status='pending'` until PO-received — **except** for a $0 quote, which has nothing to collect: no PO number required, invoice created already `paid`, `payment_status` set to `'paid'` to match (not left stuck at the hardcoded default), license active immediately. Auto-registers the buyer as a school admin if a matching `site_users` row exists; supports a single-use, 7-day, unauthenticated co-admin invite (`POST /api/quote-accept/accept/invite`). A quote can also be finalized without ever emailing it (a "Don't email this quote" checkbox on `admin-quotes.html`, for deals already agreed by phone) — `quote_sent_via` (`email`|`phone`) tracks which happened. **An FNE admin can also run the PO branch of this entirely on the customer's behalf** — `acceptQuoteViaPO()` (extracted so the admin path and the customer's own token-based path are the same function, not a duplicate) is called from `admin-concierge.html`'s "Concierge Setup" flow, reached via a button on each priced quote in `admin-quotes.html`. That same page walks an admin through the whole rest of the setup too, in this order (Release 98): 1 accept, 2 **District Administrator (required)**, 3 School License Administrator (optional; the buyer is added automatically when they already have an account), 4 invite teachers (optional), 5 district branding (optional). It shows "Still needed: a District Administrator" until one is assigned, but does not block the other steps. Each administrator step takes **any number of** School and/or District Administrators (district resolution follows `purchases.school_id → schools.district_id`, the real relationship, not just "is the buyer themselves a district admin"), setting up a starting District Branding look (logo/colors, no crop tool) once a district is linked, then inviting teachers directly into the resulting purchase's seats — for white-glove phone/email deals where the customer never touches the site themselves. Card acceptance has no admin-facing equivalent at all (PCI/compliance) — a card-paying customer always completes their own Stripe checkout.

**Quote Content Profiles** (`quote_content_profiles` table) replaced a single global set of the 4 boilerplate email sections (What's Included / Lesson Package / Video Access / License Terms) with a library of named, reusable sets — e.g. "Standard" vs. "30 Days Free Trial" — managed from a card on `admin-quotes.html`. Every quote stores which profile it uses (`quote_requests.content_profile_id`) and always renders that profile's **current** content at send/resend time (live reference, not a snapshot) — editing a profile updates every quote using it immediately. Deleting a non-default profile reassigns any quotes using it back to the default rather than blocking the delete; the default profile itself can't be deleted. `GET/PUT /api/settings/quote` no longer exposes the 4 section fields — superseded entirely by this table.

**Invoicing — two deliberately independent gates, not one:**
- **Mark Paid/Unpaid** (`PUT /api/invoices/:id`) touches only `invoices.status` → cascades to `purchases.payment_status`. Pure bookkeeping. Fires `invoice_paid` on a fresh transition to paid. Cancelling an invoice never revokes already-granted access.
- **Mark PO Received** (`POST /api/invoices/:id/po-received`) touches only `purchases.license_status` (→ `active`, sets `effective_date`). This is the real content-access gate. No financial check at all.

A school can legitimately have full content access while its invoice is still `unpaid` (admin still chasing the check) or vice versa — this is intentional, documented business logic ("give access on receipt of signed PO paperwork; track money owed separately"), not a bug. Every `invoices` row is inherently PO-sourced — Stripe/card checkouts never create one. Deleting an invoice un-links (not deletes) its purchases.

## Affiliate program

A B2B sales-affiliate program (`docs/AFFILIATE_PROGRAM_SPIKE.md` holds the design and the confirmed decisions; `docs/AFFILIATE_COMMISSION_LEDGER_SPIKE.md` covers the commission ledger). **All 4 stages (plus 3.5a/b/c) are live as of 2026-09-24**, independently re-verified 2026-09-26. Not related to the dead `brand_ambassador` membership type below, which was a consumer loyalty idea from a different project.

An affiliate is a role on the existing `site_users` system (`role = 'affiliate'`), with the detail in a joined `affiliates` row — the same split as `district_license_admins`, not a third auth system. What exists today:

- `become-an-affiliate.html` → `POST /api/affiliates/apply` (public, no auth, honeypot field + per-IP throttle) creates an `affiliate_applications` row and emails the sales-alert address. Linked publicly from the footer's Schools column (`footer.js`), so the program is discoverable to any visitor.
- `admin-affiliates.html` → `/api/affiliates/*` (all `requireAuth`) for review and management. Approving creates or promotes the `site_users` account, generates a referral code, optionally assigns one territory, and fires the `affiliate_application_approved` email with a link to get started; rejecting emails the reason. Approving an email that already has an account (teacher, parent, school/district admin) never touches that account's `site_users.role` — being an affiliate is determined by the `affiliates` row's existence, exactly like `school_license_admins`/`district_license_admins` determine those roles, since `role` is a single column that was never meant to be an exclusive gate. A district admin covering a different territory as an affiliate on the side is an ordinary case, not an edge case. (An earlier version of this refused approval outright for exactly that scenario — a real bug, fixed 2026-09-24; see `lib/access.js`'s `hasActiveAffiliateAccount()`.) A Territories button on the Affiliates tab manages assignment and revocation after the fact, for as many territories as an affiliate holds.
- **Territory is real geography now, not a free-text string** (`territories` + `affiliate_territories`, stage 3.5b — see the addendum in `docs/AFFILIATE_COMMISSION_LEDGER_SPIKE.md`). Fixed to real US states and counties. **As of 2026-09-26, a county is required for every territory** — a whole-state-only assignment can no longer be created (`findOrCreateTerritory()` in `lib/territories.js` rejects an empty county); real county *names* for every state are now pre-loaded as reference data (`server/lib/us-counties.js`, 3,143 counties, Census-derived, names only — no boundary geometry), though a `territories` row for a specific county still isn't created until first use, same as before. DC has exactly one county-equivalent ("District of Columbia" itself) from that same data, satisfying the mandatory-county rule with no special-casing. Territory is still organizational only and never decides who earns a commission. Exclusivity (one *active* affiliate per territory) is checked at the query level against the assignment's own status, per exact `territory_id` — a legacy whole-state row and a county inside it are different rows with no cross-check between them, deliberately unchanged (moot for anything created after the county rule above). Suspending an affiliate explicitly revokes their territory assignments in the same transaction, so it becomes assignable again immediately; reactivating does **not** restore it automatically, since it may already belong to someone else by then. An affiliate can hold several territories at once, with a real assignment history.
- **Every territory change now goes through admin approval — an affiliate's own request never touches an assignment directly** (`territory_requests`, added 2026-09-26). An approved affiliate can ask for an additional territory or to replace one they already hold (`affiliate-dashboard.html`, state+county dropdowns cascading off `GET /api/affiliates/counties?state=`); the application form (`become-an-affiliate.html`) uses the same dropdowns for the initial ask, though approving the application is still itself the one-step approval for that first territory — no separate request row for it. Every self-service request creates a `pending` row and changes nothing until an admin acts on it (`admin-affiliates.html`'s new **Territory Requests** tab): approving calls the exact same `assignTerritory()` the direct-admin path uses (for a "change" request, it first revokes the prior assignment in the same transaction — a true swap, not an addition), so the untouched exclusivity check applies identically either way; rejecting leaves the affiliate's existing approved territories completely untouched. The admin's own direct assign/reassign controls (the Territories modal) are unaffected by any of this — an admin acting directly never creates a request for themselves to approve.
- **A choropleth US map on the admin Affiliates page shows territory coverage at a glance** (`admin-affiliates.html`'s new **Map** tab, `GET /api/affiliates/territory-map[/:state]`). Each state is colored by its count of distinct *active* affiliates (`affiliates.status = 'active'`) holding at least one active territory there — an affiliate with several counties in one state counts once (`COUNT(DISTINCT affiliate_id)`); pending/rejected requests never affect it, since they never touch `affiliate_territories`. Color bands are computed from the actual current max count, not a fixed scale, so a handful of real affiliates still reads as visibly different shades instead of every occupied state looking the same. Click or keyboard-activate a state for a detail list below the map (affiliate name, county/counties held there, status, a link to their admin record); a plain `<select>` above the map offers the identical action for narrow screens or anyone not using a mouse. The map itself is a single static inline SVG (`us-states-map.svg`, generated once from the public-domain `us-atlas`/Census TIGER dataset via `d3-geo`'s Albers USA projection — that library was used only to generate this one file, not added as a runtime dependency) — no mapping library ships with the app.
- **Commission is a ledger**, not a column (`affiliate_commissions`, stage 3.5a — see `docs/AFFILIATE_COMMISSION_LEDGER_SPIKE.md`). One row per earning, with a status that follows the money: a card sale opens `approved` because Stripe has already taken payment, while a PO sale opens `pending` and is only approved when an admin marks the invoice paid. This exists because the earlier design recorded commission the instant a PO order was submitted — on money that had not arrived and might never. Cancelling an invoice reverses whatever hasn't been paid out, with the reason kept on the entry; an entry already marked paid is deliberately left alone and logged for manual follow-up, since that money is gone. Admins can also add a bonus or a negative correction by hand. **A reversal flips the row's status rather than writing a negative row, so every balance is filtered by status** — that rule lives in exactly one helper, `ledgerTotals()` in `server/lib/affiliate-attribution.js`, and no route computes a total inline. `purchases.affiliate_commission_cents` survives as the snapshot of what was calculated at attribution time; the ledger is what's authoritative for money owed.
- **Attribution** is 90-day last-touch on a referral code. `referral.js` (loaded on all 58 public pages) writes a `?ref=CODE` into the `fn_ref` cookie; because that's an ordinary same-origin cookie it rides along on every later `/api` call, so no checkout page needed changing. `server/lib/affiliate-attribution.js` resolves the code, and every purchase path credits the sale through the one `createPurchase()` choke point in `routes/newsletter.js`, inside its transaction. The Stripe webhook is the exception — it's a request from Stripe with no cookies on it, so the code travels in the Stripe session's `metadata.ref` instead. Commission is snapshotted at that moment, so a later rate change never rewrites past earnings, and a purchase with no known amount records the affiliate with a NULL commission rather than claiming $0. An unknown or suspended code is a silent no-op. A trial converting to an annual license inherits the trial's affiliate when no fresh cookie is present — a deliberate call rather than a confirmed decision, flagged for review in the spike. The admin's manual "add a purchase" form never attributes, since the cookie on that request is a staff member's.
- **Every mutation is audited** (stage 3.5c) — approve, reject, rate change, suspend (and the territory revocation it triggers), territory assign/revoke, and every commission transition, each recording which admin and when. This reuses `school_audit_log` rather than adding a second table: its actor/action/entity columns were already generic, so `lib/audit.js` (extracted from what used to be a private helper in `routes/school-admin.js`) writes affiliate-program rows into the same table, filtered by `entity_type` on the way back out (`GET /api/affiliates/audit-log`) so the two programs' activity never mixes on screen.
- **The affiliate has their own portal** (stage 4) — `affiliate-dashboard.html`, gated by `requireSiteAuth` (`fn_user_session`, the same site-user auth every other public-facing role uses) plus a `role === 'affiliate'` check, at a wholly separate mount (`/api/affiliate-portal`) from the admin-facing `/api/affiliates/*` — no `:id` appears anywhere in that router, since an affiliate can only ever read their own row. Shows their referral link (copy button), commission rate, active territories, pending/owed/paid totals, and their own commission ledger history — read-only; only an admin can change any of it. Discoverable from the site-wide logged-in account dropdown (`site-auth.js`), the same mechanism already used for the Parent/School Admin/District Admin/FNE Admin portal links. `AFFILIATE_LANDING_PATH` (`server/routes/affiliates.js`) now sends a newly approved affiliate here instead of to the generic profile page.

## Memberships

Three member types (`consumer`, `service_provider`, `brand_ambassador`), each with admin-editable plans (`membership_plans` — price, billing interval, trial days, Stripe sync when keys are configured). **Confirmed effectively dead as a public checkout path**: the three public signup pages `join.html`/`service-providers.html`/`brand-ambassador.html` do not exist anywhere in the current codebase (removed in the 2026-08-22 scope cleanup, see Known limitations), so `POST /api/checkout/create-membership-session` and its full Stripe subscription/webhook machinery are unreachable from any live page today. **The only live path onto a membership is the admin manual grant** (`admin-memberships.html` → `POST /api/memberships/contacts/:contactId`), which creates a `purchases` + `contact_memberships` row with zero Stripe involvement by design. `contact_memberships.status` (trialing/active/past_due/cancelled/expired) persists across the whole lifecycle; every real charge (first or renewal) creates its own new `purchases` row, which is why membership revenue shows up in Orders/Financial Insights alongside book/license purchases.

## Curriculum & content

Curriculum resources are gated by a consistent server-side matrix (`server/routes/curriculum.js`'s `gateAccess()`, applied identically on `education-portal.html`, `lesson-detail.html`; `student-lesson.html` is separately always-unlocked for an assigned classroom's students, license already covered at the teacher/classroom level): **video and every resource type (Student Handout, Classroom Poster, Teacher Copy), plus lesson-plan documents and the Quiz + Answer Key, now all require an active teacher license for both view and download** — only title/series/overview/objectives/materials/resource *labels* (not the files/video themselves) stay public. This closes a real gap that existed since launch (a long-deferred plan, finally implemented 2026-08-27): `gateAccess()` used to only strip `documents`/`quiz` for an unlicensed visitor, leaving `resources`/`videos` in the API response regardless, and the `/:id/file` endpoint had its own separate "Student Handout/Classroom Poster are publicly viewable" carve-out — together, both a URL-guessable file-serving bypass and (worse) an *unconditional*, no-check-at-all video render on `education-portal.html`'s homepage "spotlight" featured lesson, visible to literally any visitor with no navigation required. Admins always see everything, everywhere on the public site (see the auth bypass note above). Trial licenses get a metered preview (`trial_lesson_limit` curricula before everything gets stripped even for them). Every gated file download is per-resource rate-limited (`download_limit`, 0 = unlimited) and logged to `curriculum_downloads` (teacher email × curriculum × resource type).

**A parent linked to a classroom (`hasParentAccessToCurriculum()`) can VIEW Teacher Copy/Student Handout/Classroom Poster but can never download any of them, regardless of resource type** — the `/:id/file` endpoint's `forceDownload` gate (and the download-limit/logging blocks alongside it) now checks only `licensed`, never `parentCanView`. This used to be a real server-side gap, not just a missing UI restriction: `parentCanView` was OR'd directly into the same download gate a licensed teacher passes, so a parent could hit `?download=1` on any of those 3 resource types and get the raw file, counted the same as a teacher's download. `parent-lesson.html`'s Download button was removed accordingly (its `fetchAndDownload()` helper no longer exists).

Blog posts (`blog_posts`) support multiple categories, SEO fields, real scheduling (`published=true` + a future `publishDate` stays hidden until that date — genuine scheduling, not just an on/off flag), and an optional `requiresMembership` flag that strips body/video server-side for non-members (note: this membership check, not a license check, is the actual gate on locked blog posts). ## School-Admin portal

School license admins are `site_users` (`role='school_license_admin'`) linked to one or more group-license `purchases` via `school_license_admins` assignments, each carrying a **permission level**: `primary` (full access — invite, revoke, reports, co-admin visibility), `secondary` (can invite/manage but cannot revoke a seat/invitation or remove a teacher), `read_only` (view everything, write nothing). Enforcement is server-side and per-purchase (`blockIfReadOnly`/`blockIfCannotRevoke` in `server/middleware/schoolAdminAuth.js`, fail-closed by design) — **the frontend does no client-side gating by level**; a read-only or secondary admin sees every button and only gets blocked with a 403 toast after clicking.

**Invitations carry grade levels.** Every invite (school admin single/bulk, FNE concierge) must name at least one of ES, MS, HS, HE (`lib/grade-levels.js`; stored as the four full names Elementary School, Middle School, High School, Higher Education, the same strings as `site_user_audiences` and `curriculum_audiences`). They are saved on `school_invitations.audiences` (the old free-text `grade_level` column now holds a code summary such as `ES, MS`). On every acceptance path (`routes/school-invite.js` register/claim/accept-and-verify, and `claimPendingSeatsAndSubscribe` in `routes/site-auth.js`) `lib/teacher-onboarding.js` adds those levels to the teacher's own (never removing any), makes sure a `newsletter_contacts` row exists (an existing one is left as is) and puts it in the Teachers system group. The CRM list (`admin-newsletter.html`) shows a Grade Levels column from `site_user_audiences`. Registering by school email requires at least one level, and `PUT /api/site-auth/me/audiences` refuses an empty list.

School-admin accounts are created in exactly one way: **FNE-staff manual assignment** (`admin-school-admins.html` → `POST /api/admin/school-admins/assign`) — there's no self-service way for a school admin to add a peer. Teachers get onto a license two ways: an admin sends a single or bulk invite (lands on `school-invite-accept.html`), or a teacher self-registers (`education-schools.html` → `POST /api/school-registration/check`, exact email-domain match against a `purchases.school_domain`, capacity-checked transactionally) and gets nudged to notify their school admin if no seats/plan exist yet. Seats move `pending → registered → inactive/revoked`; revoking a seat or removing a teacher force-invalidates their session and, if they also held a co-admin assignment on that purchase, soft-deactivates that too with its own audit entry.

**A person who is both a registered teacher (a real `license_seats` row) and a school/district admin never counts toward that school's license totals, and never appears in its rosters/reports.** Every seat-count/roster/report query in `server/routes/school-admin.js` (dashboard, org utilization, roster, `/teachers`, reports, CSV export) excludes anyone holding an active `school_license_admins`/`district_license_admins` row via a shared `notAdminSeatClause()` helper — blanket exclusion (anywhere they hold an active admin assignment, not just for this specific school/district), matching the existing school-vs-district-admin dedup precedent already in `district-admin.js`'s `/schools` endpoint. The purchased `seat_count` (contractual total) is never adjusted; only the registered/used/available math and roster listings exclude admin-held seats — so "available" can read higher than the count of physically un-occupied `license_seats` rows for a school with a dual-role admin. The same exclusion is applied to FNE-admin-facing purchase views (`newsletter.js`'s `attachPurchaseDetails()`, opt-in via an `excludeAdminSeats` flag — used by `admin-licenses.html`'s by-domain search and `admin-newsletter.html`'s CRM purchase view, but deliberately NOT by a buyer's own self-service `my-purchases`/`my-license` view, where seeing their own seat regardless of admin role is correct).

Pages: `school-admin-login.html`, `school-admin-dashboard.html` (stats + activity feed, read-only for all levels), `school-admin-roster.html` (the real merged teacher+seat management screen — `school-admin-teachers.html` and `school-admin-licenses.html` are now dead `<meta refresh>` redirect stubs into this one, kept only for old bookmarks), `school-admin-invitations.html` (send/bulk/resend/extend/revoke/delete + CSV template), `school-admin-org.html` (read-only license/plan/co-admin info — doesn't distinguish primary vs. secondary in its own UI, only "Full Access"/"Read Only"), `school-admin-reports.html` (utilization/teachers/invitations/activity-log tabs, CSV export, read-only for all levels), `school-admin-branding.html` (see School-Level Branding below).

## School-Level Branding & District Hierarchy

A school (`schools`, backfilled from distinct `purchases.school_domain` values) can publish its own logo + primary/secondary/accent colors, applied automatically across that school's admin/teacher/classroom/student/parent surfaces via the shared `fnApplyBranding()` (`school-branding.js`) — a non-removable "Powered by Fixer Nation Education" line always stays next to a replaced logo. Draft and published branding are separate column sets on `school_branding` (`branding_status`: `DEFAULT`/`DRAFT`/`PUBLISHED`) so "Save Draft" never touches what's currently live; `server/lib/branding.js`'s `getPublishedBranding()` is the single resolution point every consuming surface calls, and returns `null` (a deliberate no-op, not a "default" object) when there's nothing to apply.

Logos can be **cropped and repositioned non-destructively** — the original upload is never modified; a stored crop rect (`{x,y,width,height}` in original-image pixels, `school_branding.draft_logo_crop`/`published_logo_crop`) is re-applied via `sharp().extract()` every time it's edited, so re-opening the crop tool always starts from the true original and "Reset" always means "back to the full image." **SVG logo uploads** are sanitized server-side (DOMPurify's SVG profile + a same-origin-only `href`/`xlink:href` filter) then rasterized once to the same PNG "display" copy every other format produces — no consuming page needed any changes for SVG support, and the crop tool works identically regardless of the original upload's format.

Schools can optionally belong to a **district** (`schools.district_id` → `districts`), which can publish its own default branding (`district_branding`, same draft/published/crop shape as `school_branding`). `getPublishedBranding()`'s resolution order is: the school's own published branding first, then its district's published branding if the school has none, then `null` — a school's own branding always overrides its district's. Districts are FNE-managed (`admin-districts.html`, `fn_session`/`requireAuth` — create districts, assign/unassign schools, invite district admins), not self-service; a **district admin** is a third role (`site_users.role='district_admin'`) on the existing site-user login (`fn_user_session`/`POST /api/site-auth/login`, same as teachers and school admins) — not a fourth session-cookie system — gated by `requireDistrictAdmin` (`server/middleware/districtAdminAuth.js`), structurally identical to `requireSchoolAdmin`. District admins get a minimal two-page self-service portal (`district-admin-login.html`, `district-admin-dashboard.html`, `district-admin-branding.html`) — branding is the only capability in scope; there's no district-level roster/invitations/reports equivalent.

## Teacher portal

## Student / classroom system

No email, ever, for a classroom-PIN student. A teacher's classroom has a `join_code`; a student registers with the code + a display name + a self-chosen PIN (`server/routes/classroom-auth.js`) and gets an auto-generated username; re-entering the same name with the matching PIN logs back into the same account instead of duplicating it. Students see only what's assigned to their specific classroom (`classroom_assignments` for lessons, `classroom_game_assignments` for Brain Games). Pages: `student-login.html`, `student-home.html`, `student-lesson.html` (full flow: overview, handout, video, pre/post reflection, one-attempt quiz, goal-setting), `student-game.html` (iframes the public brain-game page), `student-achievements.html` (goals + lesson history — no brain-game history, see below).

**The quiz can now be partially answered, saved, and resumed** — a real gap before this: `student_quiz_responses`' mere existence (any row for that student+curriculum) is the entire "one attempt" mechanism (both the server's 409 guard and the client's locked/graded view), so partial answers were previously lost the moment a student navigated away, since nothing was ever written until a fully-answered final "Submit Quiz" call. A "💾 Save Progress" button now saves whatever's currently answered to a separate `student_quiz_drafts` table (`PUT /api/student/lesson/:id/quiz/draft`) — kept structurally separate from `student_quiz_responses` on purpose, so an in-progress draft can never look like a completed attempt to the one-attempt lock. Reopening the lesson pre-fills prior selections from the draft. Drafts are cleared on final submit and by the teacher's pre-existing "Reset Quiz" button (`teacher-classroom-progress.html`), so a reset genuinely starts fresh.

**Architectural gap, confirmed and explicitly deferred (product decision, not a bug to silently fix):** the brain-games XP/badge/streak system is built entirely on the `fn_user_session`/`site_users` cookie. Classroom-PIN students' `fn_student_session` is never checked anywhere in `brain-games.js`. A student playing a Brain Game only ever produces a bare completion timestamp (`student_game_completions`, via `student.js`) — no score, no XP, no badge, no streak, ever. This is a real, scoped-but-not-built product gap, not an oversight to patch reflexively.

## Parent portal

Per-child, teacher-initiated invites only — the old shared classroom-level `parent_code` self-join flow was removed outright. A teacher invites a parent to follow **one specific student** from `teacher-classroom.html`'s roster (`POST /api/classrooms/:id/students/:sid/invite-parent`); the parent accepts via `parent-invite-accept.html`, creating a `parent_classroom_links` row keyed by `(site_user_id, classroom_id, student_id)` — a parent with two kids in the same classroom gets two independent link rows/cards. `parent-portal.html` shows one card per linked child with **completion-status progress only** (no quiz answers, no reflections — deliberately teacher-only). `parent-lesson.html` shows a curriculum's public preview plus Teacher Copy/Student Handout/Classroom Poster only (no quiz, no lesson-plan docs). A parent can never see another parent's or another student's data — every route re-checks the specific link row.

A campaign can send immediately ("Send Now"), be scheduled for a future date/time (`campaigns.scheduled_for`), or belong to a **recurring series** (`campaign_series` — daily/weekly/monthly, admin-set time + IANA timezone, runs until paused). The manual "Send Now" button is the one exception: it only marks the campaign `Sending` and returns — its first batch waits for the next `processDueBatches` tick like any other batch — because a real SMTP send must never happen inside the web request it came from. Recurrence math (`server/lib/campaign-recurrence.js`) is dependency-free, using only the built-in `Intl` API to resolve a target local wall-clock time in any IANA zone to a real UTC instant, correct across DST transitions.
